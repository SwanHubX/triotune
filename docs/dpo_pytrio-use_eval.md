## 逐步差异与来源判断

| 指标 | 差异最明显的 step | 观察与判断 |
| --- | --- | --- |
| 输入、后端 token 数；偏好对数；学习率 | 无 | 四项在 50 个对应 step 均相同，排除了 batch 大小和输入长度不同造成的差异。 |
| `train/loss` | 13 | A 0.6796，B 0.7732，差 0.0936；另有 step 9、35、42、46 的差值超过 0.03。 |
| `reward/reward_accuracy`、`reward/reward_margin` | 13 | 准确率 A 1.0、B 0.0；平均 margin A +0.0274、B −0.1495。准确率有 16/50 步不同，平均 margin 有 10/50 步异号。 |
| `reward/reward_chosen`、`reward/reward_rejected` | 13 | chosen 为 +0.0178 / −0.0555，rejected 为 −0.0096 / +0.0940（A / B）；两项共同造成该步 margin 与 loss 的差异。 |
| `time/prepare`、`time/reference` | 35、14 | prepare 最大差仅 0.0054 s；reference 在全部 50 步都是 A 较慢，step 14 为 0.483 / 0.166 s。 |
| 前反向 + 优化、总 step 耗时 | 7 | A / B 分别为 2.608 / 7.720 s、2.918 / 7.828 s；B 有 10 步的总耗时超过 5 s。 |
| token / 偏好对吞吐 | 7 | A / B 为 372 / 139 token/s、0.685 / 0.256 对/s；吞吐由相同输入量除以各自 step 耗时得到，随耗时尖峰变化。 |

训练信号方面，按相同 seed 重放抽样后，独立脚本的 1000 条偏好对与框架准备文件逐条、逐序一致；两边的 Datum 掩码和 DPO 公式也相同。但首步 loss 已有 0.004 的差值，因此后续 optimizer 更新的累积不能独自解释全部差异。第 13 步的准确率反转对应隐式奖励 margin 反转，并非准确率单独计算异常。日志没有逐条 policy/reference logprob 或初始权重校验值，也未保存运行时未提交代码的快照；不能仅凭相同 seed 确定初始状态、推理数值或请求时序中哪一项造成差异。

耗时方面，框架版逐条请求 reference logprob 并等待结果；独立版先提交四条请求，再依次等待，所以 reference 在 A 始终较慢有明确的调用方式差异。两边都调用 PyTRIO 的 `forward_backward_custom` 和 `optim_step`；B 只记录两者合计的 `time/update`，无法定位其 7.720 s 尖峰发生在哪个调用或远端阶段。A / B 的 step 耗时中位数为 2.910 / 2.711 s，B 的均值较高主要受少数慢步影响，不代表每步都更慢。

## 结论

1. 训练结果接近，但未逐步复现。两边 50 步的输入 token 数完全一致，平均 DPO loss 相差约 0.98%，偏好准确率相差 1 个百分点；第 13 步仍出现 loss 相差 0.0936、准确率 1.0 对 0.0。是否由框架设计导致：尚不能判定。样本、掩码和 DPO 公式已对齐，首步就存在差异；现有日志缺少逐条 logprob 和初始权重信息，无法定位数值来源。

2. 框架版 reference 计算稳定偏慢，50 个对应 step 都比独立版慢，均值为 0.276 对 0.097 秒。是否由框架设计导致：是。当前框架同步路径逐条请求并等待 reference 结果；独立脚本先提交同批四条请求，再等待结果。这是请求调度方式的开销，可在框架同步路径中改为批量提交。

3. 整体耗时差由慢步主导。框架版平均每步快 0.330 秒，但中位数反而慢 0.199 秒；独立版有 10 步超过 5 秒。是否由框架设计导致：没有证据表明是。两边使用相同的 PyTRIO 训练调用，独立版只记录前反向与优化的合计耗时，无法定位慢步发生在哪个远端阶段，也不能据此认定框架有稳定的速度优势。

这里的 `reward/*` 是 DPO 的隐式偏好奖励（β × policy/reference logprob 差），不是外部奖励模型打分；本实验也没有记录 GRPO 式 KL 指标。


## 修改了trainer布局之后的测试

旧版运行为 `run-20261008_143739-j2qauhy1`，新版运行为
`run-20261010_110359-coxgpmh7`；以下数据读取自两次运行的 SwanLab 本地记录。

有差距，但目前没有证据表明是计时异常：新版总耗时减少约 9.73%，三个吞吐指标均提高约 10.77%。

| 指标 | 旧版 | 新版 | 新版变化 |
| --- | ---: | ---: | ---: |
| `time/train_runtime` | 173.87 s | 156.96 s | −9.73% |
| `time/train_steps_per_second` | 0.2876 | 0.3186 | +10.77% |
| `time/train_pairs_per_second` | 0.5751 | 0.6371 | +10.77% |
| `time/train_tokens_per_second` | 206.47 | 228.71 | +10.77% |

两次均完成 **50 步、100 对样本、35,898 个输入 token**，逐步 token 数完全一致，核心训练参数及依赖版本也一致。因此，三个吞吐指标同时变化，是因为它们都用相同训练量除以总耗时，并非三个独立异常。

差距主要来自 [DPO 训练流程中的远端调用等待](../trio-cookbook/trainer/dpo_trainer.py)：

- **参考模型评分 `_reference_scores()`**：平均每步从旧版 0.456 s 降至新版 0.279 s，累计节省 **8.86 s**；新版在 49/50 步更快。
- **优化器调用 `optim_step()`**：平均从 0.464 s 降至 0.245 s，累计节省 **10.96 s**。旧版第 1、21、34、45 步出现超过 1 秒的等待，新版没有。两边中位数都约 0.239 s，说明均值差主要来自旧版的慢请求。
- **前反向计算**：新版反而累计多耗时 **2.84 s**；数据准备累计差仅 **0.006 s**。

所以，这个差距可以由远端请求延迟变化解释；但不能据此认定重构带来了稳定的性能提升。服务端排队、负载、缓存或网络都可能影响等待时间，现有客户端日志无法进一步区分。
